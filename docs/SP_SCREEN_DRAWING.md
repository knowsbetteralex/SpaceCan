# Передача изображения через SP/PUSH на ZX Spectrum 48K

## Вывод для SpaceCan

**Не используем SP для нового 8×8 корабля, пуль или отдельных звёзд.**
Продолжаем выводить их через `DRAW_1_1`: один знакоместный столбец —
это **1 байт на каждую из 8 экранных строк**. `PUSH rr` записывает
**два соседних байта** и способен испортить другой знакоместный столбец.

SP/PUSH имеет смысл попробовать позже для **длинных непрерывных
горизонтальных участков** — например, очистки одной экранной строки
шириной 20 байт в игровом коридоре, широкой буферизованной анимации
или готового горизонтального тайлового ряда.

Пока у нас выборочная dirty-cell отрисовка, экран обычно обновляется
отдельными 8×8/16×16 объектами, а не длинными непрерывными полосами.
Поэтому выигрыша от переноса SP в видеопамять не будет автоматически.

## Как работают адреса и порядок записи

Обычный `PUSH BC` занимает **11 T-states** и пишет два байта:

1. `SP = SP - 1; (SP) = B`
2. `SP = SP - 1; (SP) = C`

Следовательно, если перед инструкцией `SP = screen_address + 2`,
получится:

```text
адрес screen_address+0 : C (младший байт BC)
адрес screen_address+1 : B (старший байт BC)
SP после PUSH          : screen_address
```

Для записи **20 последовательных байт** нужно установить SP на
`screen_address + 20` и выполнить 10 `PUSH`, начиная с данных
правой части полосы. Для одинаковых нулевых байт порядок не важен.

Спрайты ZX Spectrum состоят из экранных строк, размещённых необычным
образом. **В пределах одной горизонтальной сканлинии** 32 байта идут
подряд, но следующая сканлиния **не обязана** находиться сразу за ней.
Поэтому для нескольких графических строк нельзя просто продолжать
`PUSH` в память без пересчёта адреса.

## Демонстрационная процедура (не включена в игровой рендер)

Это пример для ассемблера sjasmplus. Он **очищает ровно 20 байт одной
сканлинии**. `HL` указывает на **адрес сразу после последнего байта**
очищаемого участка. Предполагается, что вызывающий код уже работает
с разрешёнными прерываниями, как основной цикл SpaceCan.

```asm
; IN:  HL = screen_line_start + 20
; OUT: [HL-20 .. HL-1] = 0
; CLOBBERS: BC, flags. HL unchanged.
; Non-reentrant; only for one continuous bitmap scanline.
CLEAR_SCANLINE_20_SP:
    DI
    LD (SP_BACKUP),SP          ; 20 T
    LD SP,HL                   ;  6 T
    LD BC,0                    ; 10 T
    PUSH BC                    ; 11 T × 10 = 110 T
    PUSH BC
    PUSH BC
    PUSH BC
    PUSH BC
    PUSH BC
    PUSH BC
    PUSH BC
    PUSH BC
    PUSH BC
    LD SP,(SP_BACKUP)          ; 20 T
    EI                         ;  4 T
    RET                        ; 10 T

SP_BACKUP:
    DW 0
```

Внутри процедуры **запрещено выполнять `CALL`, `RET`, штатный
`PUSH` для сохранения регистров и любые операции, использующие
обычный стек, пока SP указывает на видеопамять**. Используем обычный
`RET` только после возврата SP в его исходное значение.

При обычном `IM 1` прерывание помещает PC в стек и затем вызывает
ROM-подпрограмму. Если прерывание произойдёт при `SP` в видеопамяти,
оно разрушит экранные данные и испортит выполнение. Поэтому `DI`
перед сменой SP и восстановление SP до `EI` **обязательны**.
Здесь `EI` предполагает, что у вызывающего кода прерывания
были разрешены. В общем случае флаг IFF необходимо учитывать
отдельно. Запрещается вызывать такую подпрограмму из ISR
или делать её повторно входящей.

**Подсчёт времени без ULA contention и без внешнего CALL:**
`DI 4 + LD (nn),SP 20 + LD SP,HL 6 + LD BC,0 10 + 10×PUSH BC 110
+ LD SP,(nn) 20 + EI 4 + RET 10 = 184 T`.
Внешний `CALL` добавляет 17 T, итого около **201 T**.

Для сравнения: `LDIR` для 20 байт стоит
`19×21 + 16 = 415 T` *без подготовки исходного буфера и
регистров*. Это приблизительная **теоретическая оценка, не
результат измерения на Spectrum**. Реальная экономия зависит от
ULA contention и стоимости подготовки 16-битных значений для записи.

## Куда внедрять (если будет профилирование)

1. Сначала измерить длительность рендера на бордюре или по T-states
   эмулятора, определить, сколько времени уходит на dirty-cell очистку.
2. Если появятся длинные сплошные полосы, сделать специальный
   `CLEAR_SCANLINE_20_SP` либо `DRAW_SCANLINE_20_SP`.
3. Сравнить **общую** стоимость с обычными `LDIR`, `DRAW_1_1`
   и `DRAW_1_2`, учитывая подготовку данных, `DI/EI` и адреса.
4. Только после подтверждённого выигрыша применять оптимизацию
   в рабочем коде. Текущий читабельный рендер оставить эталоном.
